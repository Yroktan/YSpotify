# Память и проверки

Бюджет Windows-сборки — до 300 МиБ private working set на оболочку и все собственные процессы при музыке. Это не гарантия для любого ПК и сеанса.

В сумму входят exe, основной процесс ECS, renderer, GPU, utility и CDM. Процессы помещаются в Win32 Job Object до запуска. Обычный Firefox пользователя не обслуживает звук. Принудительное очищение рабочего набора не применяется.

С обложками наблюдалось примерно 150–185 МиБ private working set. Последняя короткая проверка, включая обновление входа, показала пик 227 МиБ; серия замеров запуска — 176 МиБ. Точные новые отчёты сохраняются локально в quick-check.json, endurance-check.json и latency-check.json. Последняя полная проверка: трек 164,012 секунды, лицензия HTTP 200, автоматический следующий трек; пик private working set 196 МиБ, private commit 297 МиБ. Копии отчётов находятся в validation/.

Сумма обычных Working Set может составлять 450–600 МиБ из-за повторного учёта общих страниц. Private commit — отдельный показатель выделенной памяти; его нельзя выдавать за резидентную память. Старый backend с полной страницей Spotify в Firefox занимал около 590–700 МиБ.

При интерактивном входе открытая страница Google/Spotify может превышать бюджет воспроизведения. Автоматическое обновление входа также учитывается в коротком тесте с интервалом 200 мс.

Проверка --layout-only использует длинные строки, обложку и пять размеров окна. Контролируются переполнение ячеек, размеры изображения и совпадение центров обложки и паузы. Проверка воспроизведения учитывает реальное время аудио, лицензию, конец трека, следующий трек и память всех процессов.

В проверке до исправлений пять запусков занимали 2,19–4,26 с: жёстко заданный gae2-spclient задерживал команду на 1,3–2,2 с, затем получение ссылки ещё до 1,4 с. Теперь региональный сервер выбирается через официальный apresolve; для плейлистов и избранного передаётся настоящий контекст, подготовка MediaKeys и сертификата выполняется один раз. Пауза и громкость не ждут запросов библиотеки, сетевой отчёт о паузе отправляется в фоне.

Последняя серия из пяти запусков с подготовкой следующего трека: 1128, 538, 805, 484 и 442 мс. Проверяется время от запроса нативного клиента до события playing, затем отдельно успешная лицензия и продвижение позиции. Это не замер задержки динамиков. Пауза/продолжение — 0–1 мс обработки команды. Холодные запуски в разных проверках всё ещё занимали 1,1–1,8 с; максимум в одну секунду для любого трека не достигнут. Новые значения и поле targetMet смотри в latency-check.json. Предварительно подготовленный трек отдельно прослушан более12с с лицензией200 и рабочим ключом CDM: сетевое продолжение после кэшированных128КиБ проверено.

В памяти предварительно хранится не более 128 КиБ исходных данных одного следующего файла из разрешённого сервером перехода. Обычная проверка лицензии CDM сохраняется; незаконченная подготовка не задерживает новое нажатие. Ссылки файлов имеют небольшой временный кэш. Аудиобуфер ограничен, в памяти до 96 миниатюр. У обложки текущего трека собственный bitmap, не зависящий от вытеснения кэша.

Для слабых ПК чтение, декодирование и уменьшение обложек перенесены с UI в фон; при прокрутке новые обложки откладываются до остановки. Перетягивание бегунка объединяет события с интервалом 32 мс. Метрики памяти собираются в фоне не чаще раза в три секунды. Рисуются только целые строки; пустой низ списка очищается после прокрутки. Контрольный тест колеса и перетягивания показал максимум ответа UI 27,5 мс, без таймаутов.

runtime-metrics.json содержит PID и память без аккаунтных токенов. Многочасовая стабильность и другие компьютеры требуют отдельных проверок.
